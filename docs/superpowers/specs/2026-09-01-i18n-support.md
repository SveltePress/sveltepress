# Framework-level i18n support and documentation-site migration

**Status:** landing

## Requirement

> 添加 i18n 支持，同时把三个文档站点迁移成 i18n 后的版本，用新的分支实现

Add i18n support to SveltePress and migrate the three documentation sites to the i18n version, implemented on a new branch.

## Problem Statement

SveltePress site authors who need multiple languages must today stand up one complete SvelteKit site per language. The project's own documentation does exactly that: `docs-site` (English), `docs-site-zh` (Chinese), and `docs-site-bn` (Bengali) are three separate applications with identical route trees, three Netlify deployments, three domains, and three independent `sveltepress.versions.json` manifests. Language switching is a hardcoded navbar dropdown of external links (`cn.sveltepress.site`, `bn.sveltepress.site`), theme UI strings are localized through an ad-hoc `themeOptions.i18n` string bag, and there is no framework concept of a locale: no locale routing, no per-locale configuration, no per-locale output (search, `llms.txt`, sitemap). Translating a site means duplicating the whole application, and SveltePress itself ships this duplication as its own documentation.

## Solution

SveltePress gains opt-in framework-level i18n. A site author declares locales in the core plugin; each locale carries its own theme options (navbar, sidebar, UI strings, search) and its own URL prefix. The core plugin resolves the current locale from the route, exposes it through a virtual module, generates per-locale `llms.txt`, and emits a hreflang sitemap. The Default Theme renders a language switcher that preserves the current page when a translation exists and falls back to that locale's home otherwise. Version management becomes per-locale: each locale owns its manifest, its version routes, and its history.

The three documentation sites merge into one: `packages/docs-site` serves English at `/` (unprefixed), Chinese at `/zh/`, and Bengali at `/bn/`, with one Netlify deployment and redirects from the old `cn.` and `bn.` domains. Existing per-locale version history is preserved. Sites that never pass a `locales` option keep today's exact behavior.

## Grill Decisions

1. **Target architecture — one site, three locales.** The three separate sites become a single merged site with locale routing. English remains unprefixed, Chinese at `/zh/`, Bengali at `/bn/`. This matches Vitepress-style i18n and removes the triplication.
2. **Branch — `feat/i18n`.** All work lands on a new branch `feat/i18n` created from `main`.
3. **URL scheme — default locale unprefixed.** English keeps every existing `sveltepress.site/...` URL; `/zh/` and `/bn/` get prefixes. No existing English URL changes.
4. **Deployment — one site, redirects for old domains.** The merged site deploys to the current `sveltepress-main-site` Netlify site; `cn.sveltepress.site` and `bn.sveltepress.site` redirect to `/zh/` and `/bn/` so old bookmarks keep working.
5. **Merged site location — reuse `docs-site`.** `packages/docs-site` becomes the single i18n site; `docs-site-zh` and `docs-site-bn` are removed from the workspace after their content migrates into locale directories.
6. **Framework API — core `locales` option with per-locale theme.** The core plugin accepts `locales: { '/': {...}, '/zh/': {...}, '/bn/': {...} }`; each value is that locale's full theme options. A virtual module exposes the resolved current locale.
7. **Content layout — plain locale directories.** English stays at `src/routes/...` root; Chinese content moves to `src/routes/zh/...`; Bengali to `src/routes/bn/...`. No SvelteKit route groups.
8. **Versioning — per-locale manifest files.** Each locale owns its manifest (English keeps `sveltepress.versions.json`; Chinese and Bengali get locale-scoped manifests), its version routes under its locale prefix, and its own lifecycle. The CLI gains a locale selector.
9. **Language switcher — preserve page, fallback to home.** Switching locale keeps the logical page when a translation exists (e.g. `/guide/introduction/` → `/zh/guide/introduction/`), otherwise goes to that locale's home. Mirrors the existing version switch.
10. **Search & outputs — per locale.** Each locale keeps its own docsearch index (en `sveltepress`, zh `cn`, bn `sveltepress`), `llms.txt` is generated per locale at its root, and the sitemap lists all locales with hreflang alternates.
11. **Version history — preserved.** Each locale's existing manifest, `version-deltas/`, and page artifacts move into the merged site, so `/v/2026-08-28/...` and `/zh/v/2026-08-28/...` keep working.
12. **Backward compatibility — no locales = current behavior.** Without the `locales` option the plugin and theme behave exactly as today: no prefix stripping, no locale context, single theme options. Existing sites upgrade without config changes.
13. **Package scope — core + theme-default only.** i18n support lands in `@sveltepress/vite` and `@sveltepress/theme-default`. `@sveltepress/theme-blog` is out of scope.

## User Stories

1. As a SveltePress site author, I want to declare multiple locales with per-locale theme options in one plugin call, so that one codebase serves several languages without duplicating the application.
2. As a site author, I want the default locale to serve unprefixed URLs, so that existing links and search rankings do not break.
3. As a site author, I want the current locale resolved from the route and exposed through a stable virtual-module contract, so that custom themes can build their own locale-aware presentation.
4. As a site author, I want `llms.txt` generated per locale at that locale's root, so that LLM consumers read guidance in one language.
5. As a site author, I want a sitemap with hreflang alternates across locales, so that search engines understand the language versions of each page.
6. As a reader, I want a visible language switcher on desktop and mobile, so that I can read the documentation in my language.
7. As a reader on a deep page, I want switching locale to preserve the logical page when a translation exists, so that I do not lose my place.
8. As a reader following an old Chinese or Bengali bookmark, I want the old domain to redirect to the matching locale, so that the link still works.
9. As a site author, I want version management per locale, so that each language keeps its own release history and lifecycle.
10. As a maintainer, I want the official documentation merged into one i18n site, so that translations live in one place and build as one deployment.
11. As an existing SveltePress user, I want no behavior or bundle changes without a `locales` option, so that upgrading is backward compatible.

## Implementation Decisions

- The core plugin accepts a new `locales` option: an object keyed by locale prefix (`'/'` for the default locale, `'/zh/'`, `'/bn/'`, ...). Each entry carries that locale's `lang`, a user-facing `label` for the switcher, and the locale's theme options. The existing top-level `theme` option remains the contract for a single-locale site; when `locales` is absent, behavior is unchanged.
- Locale matching is prefix-based on the route path; the default locale (`'/'`) matches unprefixed paths, longer prefixes win for everything else. The plugin keeps the existing page/layout route matcher — locale directories are ordinary SvelteKit route directories, so `/zh/guide/...` is just a nested route.
- A new core virtual module exposes the resolved current locale for a route: its prefix, `lang`, `label`, plus pure helpers for locale-aware link resolution and switch targets. This mirrors the existing versions virtual module and is the public seam for themes.
- The Default Theme consumes the locale virtual module: it renders a language switcher in the desktop Navbar and the mobile navigation drawer, resolves internal links within the active locale, and switches locale while preserving the logical page when the target locale has that route (falling back to the locale home otherwise).
- The theme's existing `i18n` string bag becomes per-locale via the `locales` option; a single-locale site keeps using `themeOptions.i18n` exactly as today.
- `llms.txt` generation is locale-aware: one file per locale at that locale's root, listing only that locale's pages. The sitemap gains locale alternates with hreflang.
- Version management becomes locale-aware: each locale owns its manifest (the default locale keeps the existing `sveltepress.versions.json` name; other locales use locale-scoped manifest files), its version routes composed as `<locale prefix><base path>/<id>/...` (e.g. `/zh/v/2026-08-28/`), and its lifecycle. The CLI's `versions` commands accept a locale selector and operate on that locale's manifest. The version runtime resolves the manifest by the current route's locale.
- The existing version base-path constraint (one route segment) is relaxed to allow the locale prefix composition while keeping route-safety validation.
- The documentation migration is mechanical content movement: English content stays; Chinese and Bengali content moves into `src/routes/zh/**` and `src/routes/bn/**`; per-site configs (navbar, sidebar, i18n strings, docsearch, edit links, PWA) fold into the per-locale theme options; the `docs-site-zh` and `docs-site-bn` packages, their netlify configs, and their references in root scripts, `check-docs.mjs`, and the deploy workflow are removed.
- The deploy workflow deploys the single merged `docs-site` output; Netlify redirect rules map `cn.sveltepress.site/*` → `/zh/*` and `bn.sveltepress.site/*` → `/bn/*`.
- Existing version history is preserved: each locale's manifest, `version-deltas/`, and `.sveltepress/version-artifacts` move into the merged site under that locale's manifest.

## Testing Decisions

A good test here exercises external behavior at public seams: the virtual-module contract and generated outputs for the core, the rendered switcher/link behavior for the theme, the CLI command surface for version management, and the real merged docs site as the integration proof. Internals (prefix-matching helpers, string dictionaries) are only tested through those seams.

Proposed seams:

- **Core (`packages/vite/__tests__/`)**: locale resolution, the locale virtual module contract, per-locale `llms.txt`, and hreflang sitemap output. Prior art: `version-artifacts.test.ts`, `version-outputs.test.ts`, `versions.test.ts`, `md-svelte.test.ts` (public behavior at generated outputs).
- **Theme (`packages/theme-default/__tests__/`)**: language switcher behavior (desktop/mobile), locale-preserving switch, locale-aware link rewriting. Prior art: `version-components.test.ts`, `version-sidebar.test.ts` (component behavior), `manifestless-bundle.test.ts` (bundle behavior without a manifest).
- **CLI (`packages/cli/__tests__/`)**: locale-selected `versions` commands and per-locale manifest handling. Prior art: `cli.test.ts`.
- **Integration (repo root)**: the merged docs site must pass `pnpm check:docs` and `pnpm check:versioning-build` — the repository's own quality gates, updated to a single site with three locales.

## Out of Scope

- i18n support in `@sveltepress/theme-blog` (keeps current behavior).
- Automatic language detection or browser-negotiation redirects (locales are URL-driven only).
- New locales beyond the existing English, Chinese, and Bengali; no translation work beyond moving existing content.
- Right-to-left layout support.
- Server-side locale switching, cookies, or per-locale PWA manifests (PWA stays site-level; its strings localize through the theme i18n bag).
- Search indexing infrastructure itself (docsearch crawler configuration on the platform side).
- Migrating content that is already duplicated across the three sites in divergent form — content moves verbatim.

Each criterion names the exact command that proves it and the output that counts as passing. All commands run from the repository root on branch `feat/i18n` unless noted.

2. **Core suite green.** Command: `pnpm test:vite`. Passing: vitest exits 0 with all tests passing, including new locale, `llms.txt`, and sitemap tests.
3. **Theme suite green.** Command: `pnpm test:theme-default`. Passing: vitest exits 0 with all tests passing, including new language-switcher and locale-link tests.
4. **CLI suite green.** Command: `pnpm test:cli`. Passing: vitest exits 0 with all tests passing, including locale-selected `versions` tests.
5. **Merged site typechecks.** Command: `pnpm --dir packages/docs-site check`. Passing: `svelte-check` reports no errors.
6. **Docs content check passes.** Command: `pnpm check:docs:content`. Passing: exits 0 with no failures; the checker validates one merged site whose locale directories mirror each other.
7. **Versioned build passes.** Command: `pnpm check:versioning-build`. Passing: all three locale builds succeed and `scripts/check-version-management-build.mjs` reports success; build output contains `/`, `/zh/`, `/bn/`, `/v/`, `/zh/v/`, and `/bn/v/` routes.
8. **Old packages removed.** Command: `ls packages`. Passing: `docs-site-zh` and `docs-site-bn` are absent; `docs-site` remains.
9. **Redirects configured.** Command: `grep -r "sveltepress-docs-site-zh\|sveltepress-docs-site-bn" .github/workflows/deploy-netlify.yml`. Passing: no matches (single-site deploy); Netlify redirect config maps `cn.sveltepress.site` → `/zh/` and `bn.sveltepress.site` → `/bn/`.
10. **Full suite green.** Command: `pnpm test`. Passing: all package test suites (scripts, cli, vite, theme-default, theme-blog) exit 0.
